## 목표

**이 스프린트가 끝나면 되는 노션 기능** — 제목을 고치고, 트리에서 페이지를 끌어다 다른 자리로 옮기고, 지워서 사이드바에서 치웁니다.

B1에서 만들고·보는 것까지 됐으니, 여기까지 하면 프론트 `src/api/pages.ts`의 mock 다섯 함수가 **함수 단위로 그대로 대체**됩니다.

기준은 하나입니다. 프론트가 mock을 이 서버로 바꿨을 때, F2에서 쓴 화면 코드와 테스트가 **하나도 안 고쳐지고 통과**해야 합니다.

본문 저장 충돌은 B3입니다. 여기서는 `content`를 받아 저장만 하고 버전 검사는 하지 않습니다.

## 만드는 것

- `PATCH /pages/:id` · `DELETE /pages/:id`
- `UpdatePageInput` 계약 스키마
- 형제 순서(`position`) 중간 삽입과 재배치
- 부모 이동 + 순환 참조 차단
- 삭제 시 자손 처리
- 엔드포인트마다 통합 테스트 1개

`POST /pages` · `GET /pages` · `GET /pages/:id`는 **B1에서 이미 있습니다.** 여기서 다시 만들지 않습니다.

---

## 할 일

### 1. 수정

- [ ] `contract/page.ts`에 `UpdatePageInput` 추가 — 계약 문서와 프론트 `types/api.ts`도 **같은 날**
- [ ] `PATCH /pages/:id` — `title` `icon` `content` `parentId` `position` 부분 수정
- [ ] **필드 부재와 `null`을 구분합니다.** `parentId` 필드가 없으면 안 건드리고, `null`이면 최상위로 옮깁니다
  - zod에서 `.optional()`과 `.nullable()`을 헷갈리면 여기서 조용히 깨집니다. 테스트로 고정합니다
- [ ] `updatedAt` 갱신, `version` +1
- [ ] `title`이 512자를 넘으면 자르지 않고 `400 validation`
- [ ] 없거나 `deletedAt`이 있으면 `404 not_found`

### 2. 순서와 이동 (`lib/position.ts`)

`nextPosition(siblings)`는 B1에 있습니다. 중간에 끼워넣는 요청이 이번에 처음 생기므로 나머지 둘을 지금 만듭니다.

- [ ] `positionBetween(prev, next)` — 중간값. 간격이 `1e-6` 미만이면 재배치 신호
- [ ] `rebalance(siblings)` — `1024` 간격으로 다시 매김
- [ ] 이동은 **한 트랜잭션**에서: 부모 변경 + 위치 계산 + (필요하면) 형제 재배치
- [ ] 재배치가 일어나면 응답에 바뀐 형제들을 함께 담습니다 — 프론트가 캐시를 고칠 수 있게

### 3. 순환 차단 (`lib/tree.ts`)

- [ ] 자기 자신을 부모로 지정 → `400 validation`
- [ ] **자기 자손 아래로 이동 → `400 validation`.** 막지 않으면 트리에서 떨어져 나간 고리가 생기고, 그 페이지들은 영영 화면에 안 나타납니다
- [ ] 재귀 CTE 한 번으로 조상 사슬을 확인합니다. 부모를 한 단계씩 올라가며 쿼리하지 않습니다

### 4. 삭제

- [ ] `Page.deletedAt DateTime?` 컬럼 추가 마이그레이션 — B1에서 미룬 것입니다
- [ ] `GET /pages` · `GET /pages/:id` 두 조회에 `deletedAt` 필터 추가
- [ ] `DELETE /pages/:id` → `204`. `deletedAt`만 채웁니다
- [ ] 자손 전부에 **같은 `deletedAt` 값**을 찍습니다 (한 트랜잭션, 재귀 CTE)
- [ ] 이미 지워진 페이지를 또 지우면 `204` (멱등)
- [ ] `parentId`는 건드리지 않습니다. B5의 복구가 이 값을 그대로 씁니다

### 5. 문서

- [ ] 두 엔드포인트가 `/docs`에 요청·응답 스키마와 함께 나옵니다 — 라우트 `schema`에 `contract/`를 물리면 자동입니다. OpenAPI를 손으로 적지 않습니다

### 6. 테스트

엔드포인트마다 하나씩, 그리고 규칙마다 하나씩.

- [ ] 제목을 고치면 `version`이 +1 되고 단건 조회에 반영된다
- [ ] `parentId: null` 로 최상위 이동, 필드를 빼면 부모가 그대로
- [ ] 자기 자손으로 옮기려 하면 400이고 **트리가 변하지 않는다**
- [ ] 지우면 자손도 트리에서 사라진다. 같은 요청을 또 보내도 `204`
- [ ] 중간 삽입 50회 후에도 순서가 유지된다 (재배치가 실제로 돈다)

> 마지막 테스트가 중요합니다. [계약 문서 3번](api-contract.md#3-position-은-소수를-계속-끼워넣을-수-없습니다)의 재배치 규칙이 실제로 도는지 여기서 확인해 둡니다. F5에서 발견하면 늦습니다.

## 완료 조건

- [ ] 프론트 `api/pages.ts` mock의 다섯 함수가 이 서버로 1:1 대응된다 (B1의 셋 + 여기의 둘)
- [ ] 응답이 전부 `contract` 스키마를 통과한다 (테스트에서 `parse()`)
- [ ] 같은 요청을 두 번 보내도 데이터가 두 벌 안 생긴다 — 생성·삭제 둘 다
- [ ] 어떤 요청으로도 트리에서 떨어진 페이지를 만들 수 없다
- [ ] `pages.routes.ts` 안에 `prisma.` 0개, `pages.service.ts` 안에 `reply` 0개
- [ ] `GET /pages` 가 1000행에서 p95 200ms 이내 — 못 맞추면 그때 인덱스를 붙입니다

[공통 완료 조건](conventions.md)도 함께 확인합니다.

---

## 끝나면 할 수 있는 것

프론트 mock을 꺼도 **페이지를 만들고 · 옮기고 · 지우는 것까지** 실서버로 돕니다.
본문은 저장되지만 두 탭에서 동시에 고치면 나중 것이 이깁니다. 그건 B3입니다.
