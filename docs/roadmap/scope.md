# 백엔드 범위와 첫 목표

← [로드맵으로](../../ROADMAP.md)

---

## 백엔드에 MVP가 따로 있지 않습니다

프론트의 MVP(F1~F4)는 **백엔드가 하나도 없어도 끝납니다.** localStorage mock으로 완결되기 때문입니다.

그래서 이 저장소의 첫 목표는 "MVP"가 아니라 이것입니다.

> **프론트 `src/api/*`의 mock을 지웠을 때, 화면 코드를 한 줄도 안 고치고 그대로 도는 서버.**

B1~B4가 그 목표입니다.

---

## 판정 기준

B4가 끝났을 때 이게 되면 첫 목표 달성입니다.

1. 프론트가 `.env` 한 줄만 바꾸면 mock 대신 이 서버를 쓴다
2. 페이지를 만들고 · 쓰고 · 저장하고 · 다시 여는 흐름이 mock과 **똑같이** 동작한다
3. 두 탭에서 같은 문서를 고치면 나중 저장이 `409 version_conflict`를 받는다
4. 로그인한 사용자만 자기 워크스페이스의 페이지를 본다
5. 편집 권한이 없으면 `403`이 오고, 프론트가 읽기 전용으로 뜬다
6. 새 컴퓨터에서 명령 세 줄로 서버가 뜬다 (`docker compose up` → `migrate` → `dev`)
7. 계약 테스트가 프론트 `types/api.ts`와의 불일치를 자동으로 잡는다

---

## 넣는 것 (B1~B4)

- 워크스페이스 · 페이지 · 사용자 · 멤버십 스키마
- 페이지 CRUD — 트리 조회, 단건 조회, 생성, 수정, 삭제(휴지통 이동)
- 클라이언트가 만든 페이지 id 수용 (같은 id 재요청은 멱등)
- 본문(`BlockDoc`) 저장 + `version` 기반 충돌 감지
- 형제 순서(`position`) 계산과 재배치
- 로그인 · 토큰 갱신 · 로그아웃
- 워크스페이스 멤버와 권한 2단계 (편집 / 보기)
- 통일된 에러 응답과 요청 검증
- 계약 테스트 · 통합 테스트

## 빼는 것

| 뺀 것 | 언제 |
|---|---|
| 검색, 휴지통 복구·영구 삭제 | B5 |
| 파일 업로드, 이미지 | B6 |
| 데이터베이스(표·보드·필터) | B7 |
| WebSocket, Yjs 문서 동기화 | B8 |
| 회원가입 화면, 비밀번호 재설정, 이메일 발송 | B4 이후 별도 |
| 워크스페이스 생성·이름 변경·삭제 | 회원가입과 같이 ([B4](sprint-4.md#워크스페이스를-만드는-api는-b4에-없습니다)) |
| 댓글, 버전 히스토리, 공개 발행, 내보내기 | 백로그 |
| 멀티 리전, 큐, 캐시 서버 | 필요해지면 |

**성능 걱정으로 미리 넣는 것은 없습니다.** Redis도, 큐도, 읽기 복제본도 [성능 목표](architecture.md#성능-목표)를 실제로 못 맞출 때 넣습니다.

## 프론트와의 역할 경계

| 하는 쪽 | 것 |
|---|---|
| **프론트** | 페이지 id 생성, 블록 id 생성, 낙관적 업데이트, 자동 저장 시점 결정, 트리 펼침 상태 |
| **백엔드** | 영속화, 순서(`position`) 정합성, `version` 증가, 권한, 순환 참조 차단, 워크스페이스 스코프 |
| **둘 다 아님** | 블록 내용 해석. 서버는 `content`를 **열어보지 않습니다** (크기·형식 검사만) |

마지막 줄이 중요합니다. 프론트(`knocspace-web`) `docs/roadmap/architecture.md`의 "문서 내용은 `features/editor/` 밖에서 열어보지 않습니다"와 같은 규칙입니다. B8에서 `content`가 Yjs 데이터로 바뀔 때 서버 코드가 안 깨지려면 지금부터 안 열어봐야 합니다.
